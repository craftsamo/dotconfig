---
name: japanese-writing
description: Use when writing Japanese-language deliverable text — documentation, README, code comments, commit messages, PR titles/bodies, UI copy, error messages, release notes (日本語で書いて, 日本語ドキュメント, 日本語のREADME, 和訳, 日本語化, 表記ゆれ, 文体, 敬体, カタカナ表記, 全角半角, 一文一行, 改行位置, 助詞の省略, 複合名詞, 日本語ライティング). Covers mixed Japanese-English typography (spacing, punctuation), terminology choice (English vs katakana vs code-literal), compound-noun vs particle forms (改行位置 vs 改行の位置), notation consistency (long vowels, kana usage, dashes, 中黒), source line-breaking (one sentence per line), and per-deliverable style. This is the notation (micro) layer of the Japanese writing stack and applies to ALL Japanese deliverables regardless — for long-form argumentation also load `japanese-tech-prose`, for business documents `japanese-business-docs`, for narrative pacing `japanese-prose-rhythm`, and run `japanese-inspection` on finished drafts. Do NOT use for chat replies (the LanguagePolicy already governs response language) or for i18n/translation-file workflows.
---

<Goal>

本スキルは、日本語の成果物テキストの一貫性を保つための表記規範です。
表記は一つ、用語の決定規則は一つ、文体は成果物の種類ごとに一つに定めます。
本スキルが排除するのは、セッションをまたいで起きがちな揺れです（「Gitの履歴」と「Git の履歴」、サーバとサーバー、です・ます混在）。

</Goal>

<WhenToApply>

日本語で書かれていて、成果物として残るテキストが対象です。
具体的には、

- ドキュメント
- README
- コードコメント
- コミットメッセージ
- PR のタイトルと本文
- UI コピー
- エラーメッセージ
- リリースノート
- issue の本文

といったテキストです。

会話のチャット応答は対象外です（グローバルの LanguagePolicy に従います）。
翻訳ファイルや i18n ツーリングのワークフローも対象外です。

本スキルは日本語スタックの表記層であり、どの日本語成果物にも常に適用されます。
長文の論証には `japanese-tech-prose` を、ビジネス文書には `japanese-business-docs` を、読み物の緩急には `japanese-prose-rhythm` を重ね、仕上げの検査は `japanese-inspection` に接続します。

</WhenToApply>

<ProjectFirst>

リポジトリ自身の規約は、常に本スキルより優先されます。
次の順で参照します。

1. リポジトリ内の textlint 設定 (`.textlintrc*`) などの文章リンター。従ったうえで、検証でも実行する。
2. 明示的なスタイルガイド (`CONTRIBUTING.md`, `docs/style*`)。
3. リポジトリの既存の日本語文書で支配的なパターン。

これらのいずれでも決まらない点に限り、以下の規則に従います。

</ProjectFirst>

<MixedScript>

和欧混植（日本語と欧文や数字の混在）の規則です。

- 日本語と欧単語のあいだには半角スペースを入れる：「Git の履歴」「TypeScript で書く」。
- 数字と日本語のあいだは詰める：「3個のファイル」「12条」「100文字超」。
  数字の前後にスペースを入れるのは、欧単語や単位記号と隣り合う場合に限る。
- 日本語と全角約物のあいだ、および括弧の内側にはスペースを入れない：「（GitHub）」であり「（ GitHub ）」ではない。
- 日本語の文の句読点は全角の「、」「。」。
  日本語の地の文に半角の `,` `.` を使わない。
  並列は、欧文の語だけが並ぶ場合も「、」で区切る：「TypeScript、Docker をインストールする」。
  半角カンマの列挙は、欧文のみの括弧内列挙とコード内に限る。
- 日本語の文中で欧文だけを囲む括弧は半角 `()` でよい。
  日本語を含む括弧は全角（）。
- 数字と単位は半角で書き、単位記号の前にスペースを入れる：「100 ms」「8 GB」。
  例外として `%` と `℃` は詰める：「50%」（数字に直接続ける慣例を優先する）。
- 地の文の疑問符・感嘆符は、なるべく「。」で済ませる。
  避けられない場合は全角の「？」「！」を使い、直後にスペースを足さない。
- コードの識別子、コマンド、ファイルパス、フラグ名はバッククォートで囲み、原文のまま書く。
  バッククォートで囲んだトークンは、スペーシング上は欧単語として扱う：「`git rebase` を実行する」。

</MixedScript>

<Terminology>

日本語の地の文における技術用語は、次の決定木で表記を決めます。

1. コードの識別子、コマンド、API 名、ファイル名 → バッククォートで原文のまま書く (`repository`, `git push`, `package.json`)。翻訳もカタカナ化もしない。
2. 固有名詞（製品、サービス、言語）→ 公式の原綴りで書く (GitHub, TypeScript, Docker, Visual Studio Code)。「ギットハブ」とは書かない。
3. 地の文の一般的な技術用語 → 定着したカタカナ表記があればそれを使う。なければ英語のまま書く（固有名詞でない限り小文字）。

頻出語の参照表（定着したカタカナ表記）です。

| English | 地の文での表記 |
| --- | --- |
| repository | リポジトリ |
| server | サーバー |
| user | ユーザー |
| directory | ディレクトリ |
| library | ライブラリ |
| release | リリース |
| build | ビルド |
| test | テスト |
| deploy | デプロイ |
| merge | マージ |
| review | レビュー |
| branch | ブランチ |
| interface | インターフェース |
| parameter | パラメーター |
| error | エラー |
| log | ログ |

カタカナが未定着（または曖昧）なため英語のまま書く語は、commit hash、issue、pull request（または PR）、lint、diff、stash です。

- 同じ概念に対する複数の表記を、一つの文書内で混在させない。
- なじみの薄い用語の初出には、括弧で原語を添えてよい：「べき等性（idempotency）」。

</Terminology>

<CompoundNouns>

名詞を複合語へ融合させるか、助詞を入れて展開するか（「改行位置」と「改行の位置」）は、二つのテストと配置規則で決めます。
語彙リストでは決めません。
同じ表層形が、定着した術語にも、その場限りの圧縮にもなりうるからです（「改行コード」は、改行文字の術語でもあり、「改行されたコード」の圧縮にもなります）。

- **テスト1（展開）**：「の」または元の動詞を挿し戻し、意味が保たれるかを確かめる。
  - 意味が保たれる → その場限りの複合語。地の文では展開形を使う：「変更の内容を確認します」であり「変更内容を確認します」ではない。「エラーの原因」であり「エラー原因」ではない。
  -   意味が変わる（壊れる）→ 定着した術語。どこでも融合形のまま使う：「改行コード」(\n) ≠「改行のコード」、「環境変数」≠「環境の変数」。
- **テスト2（衝突）**：その場限りの句を圧縮した結果が定着した術語と同じ表層形になるなら、圧縮しない。動詞と助詞の形を保つ。見出しやラベルでも同様。
  - 「改行されたコード」を「改行コード」に圧縮しない（\n と誤読される）。
  - 「テストされた環境」を「テスト環境」に圧縮しない（検証用の環境と誤読される）。

テスト2を通過したその場限りの複合語は、次の配置規則に従います。

- 地の文と UI の説明文では、助詞を入れた展開形を使う：「変更の内容」「日本語のドキュメント」「削除の対象」。
- 見出し、箇条書きのラベル、表のヘッダー、UI ラベル、コミットの件名では、圧縮形を使ってよい：「変更内容」「削除対象」（体言止めと相性がよい）。
- その場限りの名詞を3つ以上連結しない。地の文では展開する：「日本語ドキュメント改行規則」→「日本語ドキュメントにおける改行の規則」。

上記の例はテストの説明であって、ホワイトリストではありません。

</CompoundNouns>

<NotationConsistency>

- 長音記号は末尾の「ー」を付ける：サーバー、ユーザー、パラメーター、コンピューター（JIS Z 8301:2019 および現行の Microsoft スタイル）。
  サーバとは書かない。
- 形式名詞や補助的な語はかな書きを優先する：
  ください（× 下さい）、できる（× 出来る）、〜のとおり（× 〜の通り）、
  〜すること（× 〜する事）、ほかに（× 他に）、〜してみる（× 〜して見る）、
  および（× 及び）、ため（× 為）。
- 送り仮名は本則に従う：「行う」「表す」「変わる」。
- 日本語の地の文と見出しでダッシュを使わない。
  em ダッシュ「—」、horizontal bar「―」、2倍ダッシュ「——」のいずれも使わない。
  同格や補足の挿入（「A——挿入——B」）は括弧（）にする。
  言い換え（「A——B」）は「。」で二文に分けるか「、」でつなぐ。
  「見出し — 副題」「**用語** — 説明」のような区切りにも使わず、全角コロンで「**用語**：説明」と書く。
  範囲を示す en ダッシュ、英語の複合語 (`Curry–Howard`)、コードブロック、書誌情報は対象外とする。
- 日本語文脈の区切りコロンは全角「：」を使う：「悪い例：」「**用語**：説明」。
  半角 `:` は、コード、URL、欧文のみの文脈に限る。
- 中黒「・」の並列は、見出し、ラベル、表、箇条書きの項目名に置く短い名詞列挙に限り使ってよい：「読者・目的・文書型の特定」。
  地の文の文中の並列は「、」または「と」「や」でつなぐ：「ビルドとテスト」であり「ビルド・テスト」ではない。
  動詞や形容の並記は、中黒でつながず括弧で添える：「書く（直す）」「読みやすく（わかりやすく）」。
  単一の固有名詞の内部では使ってよい（「ロールス・ロイス」）。
- 「〜化」「〜的」の構文と平易な言い回しのどちらかを選び、一貫させる。
  積み重ねを避ける（「最適化的な」→「最適化に近い」）。

</NotationConsistency>

<SourceFormatting>

日本語の Markdown やプレーンテキストの、ソースの改行規則です。
文体とは独立の、ファイルの折り返し方を定めます。

- 一文一行とする：「。」ごとに改行する。
  日本語の地の文を固定幅で折り返さない。
  文の途中の改行は GitHub のレンダリングで余分な半角スペースになり、固定幅の折り返しは diff を段落全体に広げる。
  一文一行なら diff は一文サイズに収まり、レンダリング上のスペースも文境界にしか現れない。
- 非常に長い文（おおむね100文字超）は、節の区切りの「、」の後で追加の改行をしてよい。
  ただし、まず二文への分割を検討する。
- 例外は次のとおり。
  - コミットメッセージの本文は git の慣習（約72桁で折り返し）に従う。こちらが優先。
  - 見出し、表のセル、単一の句である箇条書き項目は、通常どおり1行に収める。
  - コードコメントは周囲のコードの行幅の慣習に従う。

</SourceFormatting>

<Style>

- ドキュメント、README、UI メッセージの地の文は敬体（です・ます）で書く。
  一文書一文体とし、同じ地の文ブロックで敬体と常体を混在させない。
- コミットメッセージ、PR タイトル、箇条書き、表のセル、見出しは常体または体言止めにする。
  「バグを修正する」であり「バグを修正しました」ではない。
- コードコメントは常体で簡潔に書く。
  「境界値を含む」であり「境界値を含みます」ではない。
- 地の文を「ラベル: 体言止め」で代用せず、主述の通った文で書く。
  「対象: 成果物として残るテキスト。」ではなく「成果物として残るテキストが対象です。」と書く。
  例示のラベル（「悪い例：」「良い例：」）と、対応表や参照一覧のラベルは、この限りではない。
- 文中の括弧に3項目以上の列挙を詰め込まない。
  文を割って箇条書きに展開し、「〜といった」で受け直す。
- 一文一義とする。長い連用中止の連鎖より、短い文を優先する。
- 技術文書での過剰な敬語を避ける（「〜させていただく」→「〜する」）。

</Style>

<Verification>

- リポジトリに textlint（または他の日本語文章リンター）が設定されていれば、生成したファイルに対して実行し、指摘を修正する。
- 完了前にセルフチェックを行う。見る項目は次のとおり。
  - 和欧間スペースの一貫性。数字と日本語のあいだは詰まっているか。
  - 日本語の地の文に半角句読点と半角コロンがないこと（欧文のみの括弧内列挙は除く）。
  - 一文書一文体（地の文は敬体、箇条書きは常体または体言止め）。
  - 用語表の遵守と、長音表記の統一。
  - ダッシュ、許容位置以外の中黒、「ラベル: 体言止め」の地の文が残っていないこと。
- 長文やレポートなど検査に値する成果物では、`japanese-inspection` の lint と収束ループを仕上げにかける（表記ゆれの正解は本スキルが持ち、検出は検査層が受け持つ）。

</Verification>
