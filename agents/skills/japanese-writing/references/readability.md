# 読みやすさ

一読で意味が通り、読み手に余計な解釈コストを払わせないための原則（第1部）と、引っかかりやすい構文の点検項目（第2部）です。AI 特有の言い回しや過剰な和語化は references/expression.md、表記ルールは references/notation.md を参照してください。全体の設計原則は references/constitution.md が扱います。

## 第1部: 基本原則

- 修飾語は長い節から短い語の順へ: 日本語は被修飾語と述語が末尾に来るため、長い修飾節を先に置き、短い修飾語を名詞の直前に置くと保留の負担が減ります。日時や場所も大きい単位から小さい単位へ並べます。
- 読点は構造の切れ目に絞る: 息継ぎや「溜め」の演出ではなく、長い修飾節の境界、節と節のつなぎ目、誤読を防ぐ位置だけに打ちます。複文に結んだときは各節内の細かい読点を間引き、30字前後の短文には原則として読点を打ちません（B4）。二通りに読める文は読点ではなく語順で解消します（B5）。
- 一文一義（「一文一述語」ではない）: 一文に無関係な複数の主張を詰め込むと、両者の関係を読み手が推測することになります。一方で、同じ主語の前提・属性（「当館は駅前の図書館で、平日は20時まで開館しています」）、背景と変化（「以前は〜でしたが、〜」）、時間的につながる動作や反応（「異音に気づき、自転車屋に寄った」「線を引いてみると、感触が新鮮だった」）まで句点で割ると、毎回「です・ます」が鳴って稚拙なブツ切り文になります（references/expression.md X7）。主従や流れが1つにまとまる複文・重文は無理に切らず一文で通します。
- 主語と述語を離さない: 主語の直後に長い挿入節を挟むと、「最初の N 体は〜引きます」のような主述のねじれ（B2）が起きやすくなります。
- 一段落一話題と正確な接続詞: 段落冒頭で話題を示し、前後の論理関係（「そのため」は因果、「一方」は対比、「また」は追加）と一致する接続詞だけを使います。
- 読み手の前提知識に合わせる: 同じ専門用語でも、開発者向けの Issue・仕様書なら説明不要であり、一般読者向けの記事なら初出時に簡潔な説明が必要です。

## 第2部: 点検カタログ（A1〜J3）

読み手の処理負担が大きいものから順に並んでいます。いずれも**一度読んで自然に通る文は直さず、修正前後で条件・例外・留保・確信度が変わっていないか確認する**のが鉄則です。

### A1 二重否定

- 症状: 「〜ないわけではない」「〜なくはない」のように否定を重ねています。
- 直し方: 真偽と留保を保てる場合のみ肯定文へ整理します（例: 「雨天でも開催しないとは限りません」→「雨天でも開催することがあります」）。「開催します」と言い切ると留保が消えるため誤りです。
- 直さない場合: 控えめな評価自体が意図の文（「一理なくはない」）や、義務・必要条件の定型（「〜なければならない」「鍵がないと開かない」）は残します。
- 検査: reading-load の `double_negative`

### A2 従属節の入れ子

- 症状: 条件節の中にさらに条件や否定が重なり、成立条件を追えなくなっています。
- 直し方: 条件が成り立つ順に外へ出し、必要なら文を分けます。例えば「事前登録をしていない場合でも、当日受付で身分証を提示しなかったのでなければ参加できます」は「事前登録がなくても、当日受付で身分証を提示すれば参加できます」に整えます。条件の対応に確信が持てない場合は推測で畳まず確認事項にします。

### B1 長い一文

- 症状: 無関係な前提・理由・手順・結論を一文（目安90字超、エッセイは110字超）に詰め込んでいます。
- 直し方: 論点が分かれる箇所で文を分け、接続詞で関係を残します。箇条書きの1項目の中に4〜5文を詰め込んで長文化している場合は、項目を分けるか補足文を整理します。
- 直さない場合: 一つの意味や場面の流れで素直に読める40〜85字程度の複文は、単文へ刻まないでください。直前の名詞を補足するだけの後付け単文（「〜を新設しました。〜する場所です。」）を増やすより、連体修飾や「〜で、」「〜が、」で一文に結ぶほうが自然に読めます（expression.md X7 `choppy_sentence_run`）。
- 検査: reading-load の `sentence_too_long`（地の文・箇条書きとも対象）

### B2 主語と述語の距離・ねじれ

- 症状: 主語と述語が離れすぎて対応が崩れています（例: 「運営アドレスにミントされた最初の N 体は、カードを引くときに〜引きます」「一番悩んだのは、工事日程を組み直した」）。
- 直し方: 長い条件節を主語の前へ出すか文を分け、主語と述語が正しく噛み合うように整えます（例: 「運営アドレスへ最初にミントされた N 体については、抽選時に〜引きます」）。自然な主語省略がある文にわざわざ主語を補う必要はありません。

### B3 修飾語の順序

- 症状: 短い修飾語が先に置かれ、その後に長い修飾節が続いています（例: 「小さな、祖父が退職後に始めた畑」）。
- 直し方: 長い修飾節を先に出します（「祖父が退職後に始めた小さな畑」）。

### B4 読点

- 症状: 語や短い句ごとに細かく読点を打ちすぎて視線がつっかかるか、逆に長い節の境界に読点がなく誤読を招いています。特に LLM の生成文では次の3つの過剰読点が頻発します。
  - 文頭の刻み読点: ×「その後、週に一度くらい、特に予定がなくても、川沿いを歩くようになった。」（短い副詞・時制句ごとに3連続で打つ）
  - 短文の溜め読点: ×「湯気の立つお茶が、やけに温かかった。」「塗装が少し剥げた、古いベンチだ。」（20〜30字の短い文で主語や短い連体修飾の直後に余韻づくりの読点を打つ）
  - 手癖の「〜は、」「〜に、」: ×「以前は毎月1日の朝に、1時間の集計作業をしていました。」「最初の半年は、手作業で転記するだけだった。」（すぐ後ろの述語に素直に係るのに切る）
- 直し方: 節と節のつなぎ目（「〜で、」「〜が、」「〜ので、」）や長い修飾節の境界に読点を置いたら、節の中の細かい読点は抜きます（目安として1文に0〜2個、30字未満の短文は0〜1個）。
- 検査: reading-load の `excess_comma`

### B5 係り受けの曖昧さ

- 症状: 修飾語がどこに係るか二通り以上に読めます（例: 「新しい担当者の手順書を確認した」）。
- 直し方: 読点に頼らず語順で係り先を確定させます。文脈からどちらの意味か断定できない場合は推測で決めず、確認事項として報告します。

### B6 「が」の連鎖

- 症状: 一文中に接続助詞の「が」が2回以上続き、逆接なのか単なるつなぎなのか曖昧になっています。
- 直し方: 本当の対比箇所だけ「が」「ものの」を残し、他は文を切るか順接に整えます（前置きの「恐れ入りますが、〜ですが」程度は許容します）。

### B7 指示語

- 症状: 「これ」「その」の指す対象が複数考えられるか、前の段落まで戻らないと分かりません。
- 直し方: 文脈から一意に特定できる具体的な名詞へ置き換えます。候補が複数あり特定できない場合は確認事項にします。直前の文に候補が一つしかない自然な指示語まで無理に名詞へ戻す必要はありません。

### C1 漢字の連続

- 症状: 7字以上の漢字が連なり、語の切れ目が一目で分からなくなっています。
- 直し方: 長大な名詞塊だけを助詞や動詞でほぐします（例: 漢字12字の業務名を「施設予約の受付開始日時を変更する業務」のように区切る）。
- 直さない場合: **「変更内容」「環境変数」「転送記録」「調査結果」「受け入れ条件」「確定済み」「起動時」のような自然な2〜5字の漢語熟語・複合語は絶対に分解しないでください。** 無理に開くと「の」の連鎖（C2）や幼稚な文体（expression.md X11）を招きます。固有名詞・正式名称もそのまま残します。
- 検査: reading-load の `kanji_run`

### C2 「の」の連鎖と名詞化

- 症状: 格助詞「の」が3回以上続くか（例: 「デッキの版（#50）のカードの JSON のティア」「スナップショットの時点の数の上限」）、動作を名詞化して重ねています。漢語複合語を避けて語を開きすぎたときに多発します。
- 直し方: 自然な複合語に戻す（「カード定義 JSON のティア」「スナップショット時点の上限数」）か、一部を動詞・他の助詞（「における」「にある」「〜する」）に開きます。所属関係が明快な短い連鎖（「本社の受付の電話番号」）は残して構いません。
- 検査: reading-load の `no_chain`（地の文・箇条書きとも対象、括弧内の補足を跨ぐ連鎖も検出）

### C3 受け身

- 症状: 「〜と考えられています」「〜が求められています」が続き、判断や要求の主体が消えています。
- 直し方: 原文や資料から主体が分かる場合は能動文にします。主体が重要でない客観記述（「ログは7日後に自動削除されます」）や、意図的に動作主を伏せる文はそのまま残します。

### C4 カタカナ語

- 症状: 「アジェンダをシェアしてコンセンサスをアラインする」のように、空疎なビジネスカタカナ語を重ねて意味が曖昧になっています。
- 直し方: 意味が明確になる一般的な漢語・和語（「議題を共有して合意を取る」）に整えます。
- 直さない場合: **技術用語やドメイン用語（`サーバー`、`ルート`、`コントラクト`、`パッケージ`、`モジュール`、`キャッシュ`、`デプロイ`、`ミント`、`バーン`、`デッキ`、`カード`、`ティア`、`スナップショット` など）は絶対に和語へ言い換えないでください**（expression.md X11）。
- 検査: `terms` モードがカタカナ語一覧を返しますが、用語確認用の目録であり言い換えの指示ではありません。

### D1 冗長表現

- 症状: 「〜を行うことが可能となっております」「〜という形になります」など、情報を増やさない回りくどい表現が重なっています。
- 直し方: 意味と敬意の度合いを保ったまま簡潔にします（「申し込めます」「〜になります」「〜に合わせて更新します」）。可能かどうか自体が論点の文（「予約なしでも見学できます」）は残します。
- 検査: naturalness の `forbidden_phrase`、expression の `unnatural_paraphrase`、notation の `formal_wording` と `noun_wo_jikkou`

### E1 段落の偏り

- 症状: 改行のない長大な段落が続く、1〜2文ごとに空行を入れて記事やエッセイの呼吸がぶつ切りになっている、または全段落が機械的に同じ文数で揃っています。
- 直し方: 話題や場面のまとまり（目安3〜5文）ごとに段落を組み直します（文の順序は変えません）。ここぞという1か所だけの短い段落や、1文1行（改行のみ・空行なし）で書く Markdown 慣習はそのまま尊重します。
- 検査: naturalness の `uniform_paragraph_structure`

### F1 埋もれた列挙

- 症状: 同格の3つ以上の長い項目を一文の中に読点で詰め込んでいます。
- 直し方: 箇条書きに開いて一覧性を高めます。その際、各項目を機械的に「太字ラベル: 説明」の形式に揃える必要はありません。時系列の経緯であれば箇条書きにせず地の文でつなぎます（constitution.md 第3条）。
- 検査: reading-load の `buried_list`

### H1 繰り返し

- 症状: 直前の文と同じ内容を表現だけ変えて繰り返しています（「折りたたむと 20 cm になります。かばんに入るサイズです。つまり持ち運びに便利です」）。
- 直し方: 新しい情報を追加していない文だけを削ります。条件・帰結・具体例を追加している文は残します。

### H2 話題の飛躍

- 症状: 1つの段落に別の話題が混在しているか、前後の脈絡なく急に話題が切り替わっています。
- 直し方: 話題ごとに段落を分け、段落の最初の文で何についての話かを示します。見出しで話題が切り替わっている箇所に不要なつなぎ文は入れません。
- 検査: `outline` モードの見出し・段落冒頭一覧で確認します。

### H3 接続詞

- 症状: 段落や文の頭ごとに「また、」「さらに、」「そして、」が手癖で置かれているか、因果関係がないのに「そのため」でつないでいます。
- 直し方: 接続詞がなくても関係が明らかな追加は削り、逆接・条件・因果は実際の論理関係に合う接続詞を選びます。
- 検査: naturalness の `paragraph_lead_conjunction`

### I1 表記ゆれ

- 症状: 同一文書内で「申し込み・申込み」「インターフェイス・インターフェース」「カード定義・デッキの版」など、同じ対象に複数の表記や呼称が混在しています。
- 直し方: リポジトリや文書の規約、なければ notation.md の既定値と初出の定義語に統一します。コード識別子・引用・固有名詞は原文のまま保ちます。

### J1 結論の位置

- 症状: 背景や経緯が何段落も続き、この文書で何を決めたいのか・何が結論なのかが最後まで分かりません。
- 直し方: 結論・目的・求める判断を冒頭に移し、背景や経緯はその根拠として後ろに配置します（エッセイなど、意図的に結論を後ろに置くジャンルを除きます）。

### J2 用語の定義

- 症状: 想定読者が知らない略語や社内固有概念を、説明なしにいきなり使っています。
- 直し方: 初出時に簡潔な説明を添えます。反対に、想定読者が当然知っている基本技術用語（エンジニア向け文書での `ルート`、`JSON`、`キャッシュ` など）には括弧説明を付けないでください。
- 検査: `terms` モードが初出位置と周辺の補足有無を返しますが、説明の要否は必ず想定読者に照らして判断します。

### J3 二度読ませる演出

- 症状: 実務文書や技術解説なのに、「最初は A だと思っていた → 実は違った → ここで種明かし」といったドラマ仕立ての引き延ばしを挟んでいます。
- 直し方: 演出のための予告や決め台詞を除き、結論と根拠がまっすぐ伝わる構成に整えます（体験記・エッセイや、時系列自体が証跡になる障害調査ログを除きます）。
