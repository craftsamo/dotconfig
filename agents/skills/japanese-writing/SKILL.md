## 目的と基本姿勢（引き算の原則）

日本語の成果物（GitHub Issue・PR 本文、技術仕様・設計ドキュメント、記事、エッセイ、連絡文、ビジネス文書）を作成・推敲・診断するときに使います。通常の雑談、翻訳リソース（i18n）の管理、Markdown の整形のみの作業は対象外です。

このスキルは、一から人工的な文体を作る矯正ギプスではありません。**モデル本来の自然な語彙選択・コロケーション・文脈判断を活かしつつ、LLM が陥りやすい悪癖だけを引き算で取り除き、事実と論理の正確さを保つ**ために使います。

### 優先順位

1. 依頼の指示、対象リポジトリや媒体の規約
2. 既存の文書やリポジトリ内の同種成果物（既存の Issue・PR・ドキュメント）で一貫している文体・用語・表記
3. このスキルの既定値

呼び出し側（Hermes Writer など）が独自の手順を持つ場合は、その手順の中で本スキルの知識と検査を使います。

### 絶対に守る5原則

- 大人の語彙・漢語・専門用語を使う（作文調の幼児化を避ける）: 「わかりやすく書く」ことを「小学校の作文のような基礎和語（`出てくる`、`うまくいかない`、`出してくる`、`買って帰る`）だけで書くこと」と取り違えないでください。定着した技術用語・カタカナ語はもちろん、一般の記事やエッセイでも成人が自然に使う二字漢語・複合動詞・連語（`分断される`、`先送りする`、`形骸化`、`弊害`、`事足りる`、`素通りする`、`買い足す` など）をそのまま使います（references/expression.md X11）。`半年経つ`・`他のメンバー` のような常用漢字も過剰にひらがなへ開きません（references/notation.md N7）。
  - 避ける言い換え: `ルート`→`道筋`、`コントラクト`→`契約`、`パッケージ`→`部品`、`カード`→`札`、`画像`→`絵`、`追加する`→`足す`、`適用する`→`当てる`、`更新する`→`この形に直す`、`再起動する`→`止めて動かし直す`、`永続化ストア`→`状態を書き込む置き場`、`通常の抽選`→`ふつうの引き`、`未対応のため`→`〜を知らないので`、`調査結果`→`調べたこと`
  - 想定読者が共有している用語に、開発者向け Issue で `ルート（URL のパス）` と書くような不要な注釈も付けません。
- 文章の呼吸と行間を壊さない（「一文一義」≠「単文の羅列」）:
  - 同じ主語の前提・属性（×「当館は駅前の市立図書館です。平日は20時まで開館しています。」→ ○「当館は駅前の市立図書館で、平日は20時まで開館しています。」）、背景から変化への導入（「以前は〜でしたが、続けるうちに〜」）、行動と直後の感触（「〜してみると、〜だった」）まで途中で「。」と「です・ます」で切らないでください。連用形や接続助詞（「〜で、」「〜し、」「〜て、」「〜が、」「〜と、」）で自然な複文に結びます（references/expression.md X7、references/readability.md B1）。
  - 体験記やエッセイで `〜だった。`・`〜てみた。`・`〜くれた。` のような絵日記調の文末を連発したり、英語直訳の代名詞（`彼女は〜`）を置いたりせず、場面に応じた現在形や引き締まった動詞を選びます（X3、X7）。直前の名詞を補足するだけの後付け単文（×「質問箱を新設しました。誰でも投稿できる場所です。」→ ○「誰でも投稿できる質問箱を新設しました。」）や、1〜2文ごとの細切れ段落も避けます。
  - 読点（`、`）を打ちすぎない: 単文を「〜で、」「〜ので、」と複文に結んだときは、節の中の細かい読点を間引きます。文頭の短い副詞・時制句ごとに連続で打つ刻み読点（×「その後、週に一度くらい、特に予定がなくても、…」）や、20〜30字の短文で余韻を作る溜め読点（×「お茶の湯気が、やけに温かかった。」「塗装が少し剥げた、古いベンチだ。」）、素直な語順での不要な「〜に、」「〜は、」を避けてください（readability.md B4）。
  - 具体的な会話・情景の直後に意味を解説する答え合わせ、前後から自明な理屈の補足（「翌朝使う→今から注文しても間に合わない」など）、聞かれてもいない否定（「〜わけではない」「A というより B」）、記事末尾の再要約や予防線ラッシュを避けます（X6、X12）。
- 文体と表記のレベルを揃える: 指定や既存慣習がない限り、記事・ガイド・連絡文・GitHub の Issue や PR の本文は**落ち着いた「です・ます」調**を既定とします。「だ・である」調は論文・公的文書・規程や常体のエッセイで使います（notation.md N9）。「です・ます」調の地の文にリズム目的で常体の現在形（「〜てしまう。」）や芝居がかった「〜たのです。」を混ぜず、「〜する形です」の緩衝表現や語彙の幼児化も避けて正確な漢語・専門用語を使ってください。また、英字・コード・英字単位（`Git の履歴`、`100 MB`）には半角スペースを入れ、数字と日本語の年月日・助数詞（`10月8日`、`10秒`、`最大8回`、`第4版`）は詰めて書きます（N1、N2）。
- 意味と事実を変えない: 主張・比重・確信度・条件・留保を変えず、手元にない固有名詞・数値・体験を推測で作らないでください（references/revision.md R1、R2）。別の言い方ができることは書き換える理由になりません。
- 検査結果は候補であり命令ではない: `scripts/inspect_text.py` は機械的な点検候補を返すツールです。文脈上自然な表現や分野の慣用は、無理に書き換えず理由を持って残します。

## 依頼別の進め方

| 依頼の種類 | 例 | 手順 |
|---|---|---|
| 書く | 「Issue を書いて」「記事にまとめて」 | 下のワークフロー 1〜5 |
| 直す・推敲する | 「読みやすくして」「AI 臭さを消して」「校正して」 | 1で読み手と目的を確認し、3で原文を検査、4で判断・修正後に `original` 付きで再検査し、5で仕上げて報告する（診断のみで止めない） |
| 診断する | 「この文章を採点して」「どこが不自然か見て」 | references/evaluation.md「診断」に従い所見を返す（検査は references/inspection.md）。改めて依頼されるまで本文は書き換えない |
| 表記を整える | 「表記ゆれを直して」 | references/notation.md と `notation` モードで表記のみ整え、変更件数を報告する |

作業の深さは2段階です。迷ったら **quick** で進め、`full` も選べる旨を一言添えます（`full` を求められたときに手順を黙って省かないこと）。

- quick（既定）: 読み手・目的・構成を頭の中で整理して執筆・修正し、検査を1回以上実行して引っかかりだけを直します。
- full: 社外公表・経営層向け文書、1万字超の長文、または「しっかり」「丁寧に」と指定された場合に使います。構成案を書き出し、全モードで検査し、references/evaluation.md の6観点で採点（各90点以上・平均92点以上）します。レビュー用サブエージェントを使える環境では、構成・読みやすさ・表現のレビューを並行委任し、最終判断と本文修正は自分で行います。

## ワークフロー

### 1. 設計（書く前に決めること）

- 読み手と目的: 誰が読み、読後に何を判断・実行するかを明確にします。不明で成果物が大きく変わる場合のみ短く質問します。
- ジャンルと文書型: 技術文書（`tech`）、ビジネス文書（`business`）、記事・コラム・ブログ（note など）、エッセイ（`essay`）、やさしい日本語を書くときは、執筆前に必ず references/genres.md の該当節を確認します。議事録（minutes.md）、調査報告書（report.md）、手順書（guide.md）、企画・提案メモ（memo.md）、スライド構成案（slide.md）に該当するときだけ `references/doctypes/` の該当ファイルを読みます。GitHub Issue・PR や技術仕様は genres.md の `tech` に従い、自治体提案書などの型を無理に当てはめません。
- 骨格と材料: 中心となる結論・目的を冒頭に置き、見出しだけで全体の構成が追えるようにします。必要な固有名詞・数値・一次情報が欠けている場合は捏造せず、依頼者に確認するか本文に `【要確認: 内容】` と明記します。依頼されたときのみ文体プロファイル（assets/style-profile-template.md）を作成・参照します。

### 2. 執筆

素直で自然な日本語で書きます。構成の判断は references/constitution.md、表記の基準は references/notation.md に従っており、執筆中に過剰な言い換えや自己検閲をする必要はありません。細かな癖はステップ3の検査で拾います。

### 3. 検査

references/inspection.md に従って `scripts/inspect_text.py` を実行します（一時ファイルまたは `--request` の標準入力を使用し、作業ファイルは残さない）。既存の文章を直す場合は `original` に修正前の本文を渡して `revision` モードも実行します。実行環境がなく動かせないモードは「問題なし」と偽らず「未検査」と報告し、inspection.md の手動点検に切り替えます（自動インストールや権限変更はしない）。

### 4. 判断と収束

指摘を一つずつ「直す・残す（理由付き）・情報不足」に仕分けます（references/revision.md「判断台帳」）。判断に迷う項目だけ該当リファレンスを参照してください。

| 指摘の参照先 | 読むファイル |
|---|---|
| `expression.md` X1〜X12 | references/expression.md |
| `readability.md` A1〜J3 | references/readability.md |
| `notation.md` N1〜N11 | references/notation.md |
| `revision.md` R1〜R5 | references/revision.md |

修正後は関係するモードで再検査し、新たな指摘が出なくなるか、同じ箇所で指摘が裏返る状態になったら止めます（指摘ゼロを自己目的にしない）。

### 5. 仕上げと報告

全文を音読するように見直し、不自然な言い回し・コロケーションの崩れ・「の」の連鎖・主述のねじれがないか確認します。あわせて references/evaluation.md の6観点を満たしているか点検します。

- 書いたとき: 成果物と、確認が必要な点（あれば簡潔に）。`full` では6観点の評価結果も添えます。
- 直したとき: references/revision.md「直したときの報告」（変えたところ・残した表現・確かめたい点）の形式で報告します。
- 診断したとき: references/evaluation.md「診断の報告」の形式で報告します。
- 表記を整えたとき: 整えた本文と変更種別ごとの件数（意味に関わる疑問は直さず確認事項へ）。
