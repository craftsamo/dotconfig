<Goal>

Single source of truth for the registry's structure. The engine (`scripts/pp`) and the
schema (`schema.sql`) conform to this document. The SQLite DB at
`~/Workspaces/Personal/People/data/people.db` is authoritative; JSON/CSV under
`data/export/` is a regenerable mirror (never hand-edited). Data is **sensitive** — handle
per `Personal/AGENTS.md`.

</Goal>

<Principles>

- **Canonical registry.** One row per person in `persons`, keyed by a stable **bare slug**
  id (`ar`, `oy`, `master`). That id == the `person_id` every consumer references, so it
  must not change casually (`rename-person` rewrites all FKs if it ever must).
- **Stable, state-free ids.** State lives in `review_status` (data confidence:
  `needs_review|confirmed|ignored`) and `status` (lifecycle: `active|inactive`), never in
  the id. Inactive people are kept (`set-status`), never deleted.
- **Normalized lookup.** Aliases and contact handles store a normalized form
  (`alias_norm` / `handle_norm`, NFKC + casefold + collapse spaces; handles also strip `@`
  and `t.me/`, `github.com/`, `x.com/` prefixes) so a sender handle or name resolves to a
  person.
- **Code registries.** `countries` (ISO 3166-1 alpha-2), `languages` (ISO 639-1), and
  `contact_channels` are lookup tables so nationality / residence / language / channel are
  consistent and joinable (e.g. against the budget's `country` tag axis). Registries
  auto-extend on demand.
- **Don't infer.** Unknown fields are `null` / empty; a multilingual person's
  `preferred_language` stays null until stated. Prefer `review_status = needs_review` over a
  guess.
- **Privacy invariant.** Sensitive channels (`phone`, `email`) are flagged `is_sensitive`
  and not populated by default. Never store gov IDs, home addresses, secrets, or wallet keys.
- **Versioned.** Schema evolves via `migrations/` (`pp migrate`); baseline is
  `user_version = 1`.

</Principles>

<IdentityState>

| entity   | id form                          | sentinel         |
|----------|----------------------------------|------------------|
| person   | bare slug (`ar`, `oy`, `master`) | `person_unknown` |

`review_status ∈ {needs_review, confirmed, ignored}` and `status ∈ {active, inactive}` on
every person. `kind ∈ {self, individual}` — `self` marks the operator's own record
(`master`), which is not a counterparty. The `person_unknown` sentinel always exists and is
`confirmed`.

</IdentityState>

<CoreTables>

- **persons** `{id, display_name, kind, status, review_status, residence_country?,
  preferred_language?, preferred_contact_channel?, timezone?, last_updated?, created_at,
  updated_at}`.
- **person_aliases** `{person_id, alias, alias_norm, is_primary}` — the canonical
  display_name is the primary alias; variants enable name lookup.
- **person_contacts** `{person_id, channel, handle, handle_norm, is_primary}` — multiple
  handles per person; `channel` references `contact_channels`.
- **person_languages** `{person_id, language, proficiency?, is_primary}` —
  `proficiency ∈ {native, fluent, conversational, basic}`.
- **person_nationalities** `{person_id, country, is_primary}` — supports dual citizenship.
- **person_notes** `{person_id, seq, text, created_at}`.
- **person_tags** `{person_id, axis, value, value_norm}` — flexible axes registered in
  `person_tag_axes` (e.g. `comms`, `how_we_met`, `team`, `interests`, `availability`); add a
  new axis without a schema change. Reserve `comms` for global tone/style prefs.
- **person_relationships** `{from_person_id, to_person_id, type, note?}` — directed edges
  (`colleague`, `supervisor`, `reports_to`, `friend`, `family`, …).
- **person_audit** `{seq, person_id?, ts, action, tbl, field?, old_value?, new_value?,
  note?}` — append-only change history (Personal is git-less). No FK so it survives
  delete/rename/merge.

</CoreTables>

<MembershipMirror>

`Projects/<project>/teams/members/<person_id>.json` is the **source of truth** for project
membership; `pp import-projects` rebuilds these from disk (project id == the Projects dir
slug, e.g. `ExampleProject`):
- **person_project_memberships** `{person_id, project_id, status?, working_relationship?,
  can_merge, can_deploy, source_path, last_synced_at}`.
- **membership_roles / _responsibilities / _areas** `{person_id, project_id, value}`.
- **membership_permission_scopes** `{person_id, project_id, action ∈ {approve, review},
  target}` — the list-valued `permissions.can_approve` / `can_review`.
- **membership_notes** `{person_id, project_id, seq, text}` (comms prefs live here).
- **membership_contacts** `{person_id, project_id, channel, handle}` (project_contacts).

Children cascade-delete with their membership and (transitively) with the person.

</MembershipMirror>

<ExportMirror>

Regenerated by `pp export`; re-importable by `pp import-json`:
- `config/{countries,languages,contact_channels,tag_axes}.json` — the registries.
- `entities/persons.json` — persons with nested aliases/contacts/languages/nationalities/
  notes/tags/relationships.
- `entities/memberships.json` — the membership mirror (person_id + nested roles/perms/…).
- `csv/*.csv` — flat tables for inspection.

</ExportMirror>

<CLISeam>

Mutations are flag-driven (no draft files): `upsert-person`, `set-status`, `confirm`/
`ignore`, `rename-person`, `merge-person`, `alias-*`, `contact-*`, `lang-*`, `nat-*`,
`note-add`, `tag-*`, `rel-*`, `import-projects`. Read seams for consumers: `whois`
(resolve handle/name → person_id + context), `show`, `list`, `search`. Every mutation
writes a `person_audit` row.

</CLISeam>

<Consumers>

The join key is **`person_id`** (== `persons.id`) everywhere. Cross-store integrity is
verified by **direct, read-only reads of the other store's live DB** — the export mirror is
for inspection/backup, **not** validation, so checks are never stale.
- **household-budget** — `counterparties.type='person'` rows carry `person_id` (a soft
  reference to `persons.id`, like `projects.dir_path`). `hb validate` opens `people.db`
  read-only and verifies each person counterparty resolves; `pp validate` opens `budget.db`
  read-only and verifies the same edge from this side (mutual). Either skips with a warning
  if the other store's DB is absent. Both accept `--people-db` / `--budget-db` overrides.
- **message-reply** — `pp whois` resolves the sender against the **live** DB; the reply uses
  `preferred_language` / `languages`, tone from `working_relationship` + `comms` tags +
  `relationships`, framing from membership `roles`/`responsibilities` + `notes`, and scope
  from `permissions`.
- **Projects** — `teams/members/*.json` (the source of truth; not a DB) reference People by
  `person_id`; `pp validate` reads those files directly and enforces that every member
  resolves to an existing person.

</Consumers>

<Extensibility>

- **New tag axis** → register in `person_tag_axes` and start tagging; no schema change.
- **New core field/relation** → a numbered migration under `migrations/` (`pp migrate`).

</Extensibility>
