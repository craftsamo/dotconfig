# Blog Source Drafts

There is no universal blog Markdown dialect. Use the specified CMS or
repository conventions first. Without a named engine, draft portable
Markdown headings, paragraphs, lists, quotes, links and fenced code as
authoring notation, not as evidence those features render at the destination.

Tables, raw HTML, footnotes, custom callouts, embedded scripts, image sizing
and captions are engine-dependent. Ask only when an unknown capability
changes a requirement; otherwise use a simpler representation and state
that destination rendering is unverified. Do not add plugins or modify a CMS.

Preserve supplied slugs, metadata and links rather than inventing a deploy
workflow. Image URLs must be supplied or returned from an authorized producer;
a hypothetical upload URL is not a valid placeholder. A source draft with
unresolved media or editor work is not a published or preview-verified article.

## Shape the Reader's Route

If the brief identifies a novice reader seeking an explanation, connect the
opening to their question and introduce a function before its unfamiliar
name. If readers already know the topic, start at the new distinction instead.
Use the supplied audience and house notation; when either is unknown,
preserve supplied usage rather than inventing a house style or reader profile.

Locally authored example (hypothetical explanatory passage):
For readers asking why an old page still appears: "The browser can keep a
local copy of a page and reuse it. That copy is a cache; it may not contain
the latest change."
Reason: a recognizable event gives the term a referent and the last clause
limits the explanation. "This article explores caching comprehensively"
adds no answer and would overpromise if the body covers only browser copies.

Retain: a short "Background" section that supplies necessary context, or
established terminology for specialist readers. Not every heading needs a
conclusion and not every blog needs an anecdote, summary or promotional close.
Allocate space to the reader's difficult question rather than making every
section equally long. Keep a real parallel list when it helps lookup.

QA evidence: read the title, headings and paragraph openings to trace the
promised answer, then quote the body passage that actually supplies it.
Identify an unexplained dependency or missing source concretely; do not
equate an unknown audience convention with a defect or verified CMS behavior.
Check that notation choices do not change supplied terms, links or qualifiers.
