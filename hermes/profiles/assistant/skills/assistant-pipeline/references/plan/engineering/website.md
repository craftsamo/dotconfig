# Website / homepage — plan recipe

Multiple pages sharing one identity. What distinguishes it from an LP
is the IA: page inventory, navigation, and shared layout must be fixed
before any page is built, so IA is always its own first Wave.

## Brief — fix before the session

- **Purpose & audience** — what the site must accomplish; primary
  visitor journeys.
- **Page inventory** — known sitemap, or the inputs to derive one
  (existing material, competitor references). Unknown → deriving it IS
  Wave 1, never skipped.
- **Content sources per page** — who writes what (writer stages,
  user-provided, reuse); imagery per section (creator + Budget).
- **Brand & style** — logo, palette, tone; reference sites.
- **Cross-cutting needs** — SEO/OGP metadata, analytics, contact form,
  multilingual — each named explicitly or explicitly out.
- **Deploy target & domain.**

## Wave prompt — add to the base-session prompt

> Multi-page site. Wave 1 must fix IA: sitemap, navigation, shared
> layout/design tokens. Later Waves build page groups on that layout;
> cross-cutting concerns (SEO/OGP, analytics, forms) are named Waves,
> not footnotes. Deploy last.

## Expected outline — inspection standard

- IA/layout Wave first; page-group Waves independent of each other
  once the layout lands (parallelizable across session turns).
- Cross-cutting concerns appear as their own Waves.
- Red flags: one giant "build all pages" Wave; page Waves before a
  layout Wave; CMS/backend Waves the Brief never asked for.

## Defaults

- New repo: the frontend-platform derivative of the local starter
  family (discovered per `bootstrap.md`) — bootstrap Wave 0.
- Authority `A1`; `A2` when the user wants PR-per-page-group.
- Verification: rendered screenshots per page group (mobile +
  desktop), metadata spot-check on the live URL.
