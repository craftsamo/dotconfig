# Existing-repository change - Client guide

Supply the requested behavior or question, current symptoms, scope exclusions,
known reproduction steps and acceptance expectations. An existing Issue, plan
or PR is context; do not rewrite or split it before OpenCode can investigate.
Issue registration/updates require an explicit user request for this job.

Assessing, adding to or improving managed hands reference catalogs is
existing-repository maintenance, not media production. Relay the desired outcome,
known target and evidence, distinguishing assessment-only from requested changes
and observations from suggestions. If the leaf or field is unknown, OpenCode
investigates from the purpose or a bounded inventory; do not demand technical
filenames or fields from the user or invent them. Findings alone never authorize
repairs or factual-status upgrades. OpenCode's `hermes-hands-references` skill
owns the maintenance procedure.

OpenCode owns code-grounded planning. Do not prescribe per-file
changes, a fixed unit count or an approach already supplied by OpenCode's skills.
Preserve meaningful distinctions: a refactor keeps behavior, a bug fix addresses
the reported symptom, performance work needs measured comparison, and a rebuild
must preserve data and provide a recovery path.

One implementation approval releases the agreed change through PR delivery.
Scope changes return to the user; routine sequencing remains OpenCode's.
Acceptance checks the observed requested outcome, regression evidence, scope
and unresolved risks. A findings-only review or diagnosis does not authorize fixes.
