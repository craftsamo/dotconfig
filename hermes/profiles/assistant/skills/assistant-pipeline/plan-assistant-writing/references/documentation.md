# Documents — decision surface

Technical and business text readers use to understand, decide, act or look up
information. Writer type `document` · QA `prose`. Use `write-document`,
`edit-document` or `analyze-document`; existing briefs saying documentation or
business-document select this family, not the legacy writing workflow.

## Select the operation

- Write: a defined purpose, reader and format, with the materials needed to
  support the requested facts. An outline unit stops before full prose; a
  piece follows its approved outline; a small whole job needs no ceremony.
- Edit: the original and named changes, with protected facts/sections and
  scope. Wording is the default; structure changes or a new purpose require
  explicit release. Do not overwrite the source without authorization.
- Analyze: the existing text and question; supplied criteria only to the
  extent needed. Compare mode needs both texts. A descriptive question need
  not produce defects or a replacement document. Advice before text exists
  remains a consultation, not an invented analysis.

## Fix the conditions that affect the work

Infer already answered fields before asking. The public leaf's form and
selected local reference own writing mechanics; do not copy their procedures
into the brief or require every format's fields for every document.

| Format | Relevant inputs and boundaries |
| --- | --- |
| readme / guide / reference | Reader task, version/platform scope, real commands and behavior from supplied engineering evidence; existing terms and conventions |
| report | Question, period/population, method, results and known limitations; observation is distinct from interpretation |
| minutes | Notes/transcript, actual decisions and attributions; missing owners/deadlines must not be assigned |
| proposal | The decision to discuss, real alternatives/constraints and any actual requester position; no invented recommendation |
| slides | Written presentation outline and producer requirements; no claim of rendered layout or speaking duration |
| release-notes | Known changes, release status and adoption requirements; no inferred dates or compatibility |
| issue | Observed/expected behavior or feature goal, supplied reproduction/environment and sanitized evidence; no bug investigation |

Custom formats follow the supplied contract. Preserve mixed-document sections
where appropriate instead of forcing all material into a single template.
Missing from the record is not a decision to leave a matter open. Conflicting
sources go back for clarification, not silent reconciliation.

Source material, style examples and document templates have different roles.
Require sources for factual corrections, records and runtime claims. Writer
may document supplied evidence but does not execute commands, reproduce
research or inspect production systems. A missing fact that prevents the
requested result is a spec-gap, not permission to fill a plausible answer.

## Release and acceptance

Name the durable delivery path, unit, scope, required content and any hard
bounds. The requester owns decomposition and acceptance; a doc-set restructure
inside a single-file edit is a granularity finding. Pass approved outlines
and actual versions to dependent pieces without reopening settled decisions.

Use the served document gate, with checked / unmet / unverified criterion
evidence rather than four legacy passes or lint output. Humanizer is
explicit-request only. A text-only acceptance does not certify runtime
behavior, rendering, missing assets or public availability. Repository
integration and commits remain the engineer's work, consuming accepted text.
