# Explainer Video Authoring

Author HTML/CSS/GSAP for this task, not a generic explainer-template DSL.
`theme`/`style`/`direction` are concrete recipes to adapt, not a scene graph
to instantiate. Output canvas is one of two fixed ratios, always 30fps:

| `aspect` | dims        |
| -------- | ----------- |
| `16:9`   | 1280x720    |
| `9:16`   | 720x1280    |

No arbitrary size is accepted. `renderer` is an explicit engine choice made in
the proposal and never silently switched afterward: `hyperframes` (plan
`version: 1`) authors HTML/CSS/GSAP as described below; `motion-canvas` (plan
`version: 2`) authors a Motion Canvas `scene.tsx` instead — see
[motion-canvas](motion-canvas.md) for that engine's own source/plan/runtime
contract, which this document does not repeat. Prefer Motion Canvas for
reactive diagrams, algorithms and Canvas-based explanation; prefer HyperFrames
for HTML/UI or media-oriented compositions. An old `version: 1` plan that
named `renderer: motion-canvas` before Motion Canvas existed is a discussion-
only artifact: it stays non-executable, and a Motion Canvas render always
needs a fresh `version: 2` proposal and a new approval, never reuse of that
old hash.

## Plan Contract (`plan.json`)

VideoCreator writes `plan.json` (via `propose`), NOT the client, and only from
client-approved topic/audience/goal, an approved script, and real supplied
assets — nothing invented:

```json
{
  "version": 1,
  "topic": "How a bicycle derailleur shifts gears",
  "audience": "Curious teens with no mechanical background",
  "learning_goal": "Understand why moving the chain between sprockets changes gear ratio",
  "theme": "workbench",
  "style": "flat-vector",
  "direction": "mechanism",
  "must_keep": "Derailleur must be labeled correctly; do not invent unapproved brand names",
  "renderer": "hyperframes",
  "duration": 20,
  "aspect": "16:9",
  "character": {
    "framing": "bust",
    "performance": "still",
    "lip_sync": "cues",
    "body": "assets/character-body.png",
    "video": null,
    "mouths": {"rest": "assets/mouth-rest.png", "open": "assets/mouth-open.png"},
    "cues": "assets/cues.json",
    "sync": null
  },
  "audio": {
    "mode": "speech",
    "master": "assets/narration.wav",
    "script": "assets/script.txt",
    "receipt": null,
    "captions": null,
    "timing": null
  },
  "units": [
    {"id": "u1", "start": 0, "end": 10, "goal": "Introduce the derailleur and the chain path",
     "narration": "This is a derailleur. It moves the chain between sprockets.",
     "before": "Chain sits on the smallest rear sprocket", "change": "Derailleur arm swings inward",
     "after": "Chain sits on a larger rear sprocket"},
    {"id": "u2", "start": 10, "end": 20, "goal": "Explain why the ratio changes",
     "narration": "A bigger sprocket means more turns of the pedal per wheel turn, so pedaling feels easier.",
     "before": "Small sprocket, harder pedaling", "change": "Chain climbs to a larger sprocket",
     "after": "Larger sprocket, easier pedaling"}
  ],
  "copy": [
    {"id": "c1", "text": "The derailleur moves the chain", "start": 1, "end": 9},
    {"id": "c2", "text": "Bigger sprocket = easier pedaling", "start": 11, "end": 19}
  ],
  "samples": [
    {"at": 0, "expect": "Opening frame with the labeled derailleur"},
    {"at": 5, "expect": "Chain mid-shift between sprockets"},
    {"at": 15, "expect": "Chain settled on the larger sprocket, ratio callout visible"},
    {"at": 19.966666666666665, "expect": "Final visible frame retains the ratio callout"}
  ],
  "assets": {
    "assets/gsap.min.js": "<sha256>",
    "assets/GSAP-LICENSE.txt": "<sha256>",
    "assets/gsap-provenance.json": "<sha256>",
    "assets/character-body.png": "<sha256>",
    "assets/mouth-rest.png": "<sha256>",
    "assets/mouth-open.png": "<sha256>",
    "assets/narration.wav": "<sha256>",
    "assets/script.txt": "<sha256>",
    "assets/cues.json": "<sha256>",
    "assets/mouth-track.js": "<sha256>"
  },
  "pending": []
}
```

Illustrative schema example only, not a real test fixture (the actual
regression fixture uses an unrelated cache-flow topic); never a real or
client-approved explainer. `mouth-track.js` in the source's `assets/`
directory is generated by `propose` from the approved `cues.json`, never
authored or supplied by hand. Field-by-field bounds, matching
`scripts/explainer.py`'s `model()` exactly:

- Top-level keys are exactly `version, topic, audience, learning_goal, theme,
  style, direction, renderer, duration, aspect, character, audio, units,
  copy, samples, assets, pending, must_keep` — no extra or missing field.
- `version` must be the integer `1` (HyperFrames) or `2` (Motion Canvas), and
  must match `renderer`: `renderer: hyperframes` requires `version: 1`;
  `renderer: motion-canvas` with `version: 1` is a legacy discussion-only
  plan and always appends "Legacy Motion Canvas discussion-only plan; issue
  a new version 2 proposal, never reuse its approval" to the computed
  missing list reported in `RESULT` — the raw `spec.pending`/`plan.json`
  field is left unchanged; it can never itself be executable. Only
  `renderer: motion-canvas` with `version: 2` is a real Motion Canvas
  proposal (see [motion-canvas](motion-canvas.md)).
- `topic`/`audience`/`learning_goal`/`theme`/`style`/`direction`: nonempty
  text, 1..4000 characters, no control characters. `must_keep` is the same
  limit but may be an empty string.
- `renderer`: `hyperframes` or `motion-canvas`, as above.
- `duration`: `1..180` seconds; a `version: 2` (Motion Canvas) plan
  additionally requires `duration` to land exactly on a 30fps frame
  boundary.
- `aspect`: exactly `16:9` or `9:16` (fixed dims per the table above).
- `assets`: the COMPLETE approved map of every file under `assets/`
  (relative path -> SHA-256), at most 160 entries. Every key matches
  `assets/[a-zA-Z0-9_./-]+` with no `..` segment and no double slash, and
  every value is a lowercase 64-hex SHA-256. `freeze` rejects a source whose
  actual `assets/` contents differ from this map in either direction.
- `pending`: a bounded list (<=30) of short text items (<=2000 chars),
  naming both the missing dependency and the producing role/hands (e.g.
  "approved character body image via image-creator's mascot leaf"). Never
  invented file paths or hashes — a genuinely missing input is named here,
  not silently substituted.

## Character Contract

`character` keys are exactly `framing, performance, lip_sync, body, video,
mouths, cues, sync`. See [character](character.md) for the full
framing/performance/lip_sync combination table; the binding rules the
helper enforces are:

- `framing`: `none`, `bust` or `full`. `performance`: `still`, `puppet` or
  `animated`. `lip_sync`: `off`, `cues` or `baked`.
- `framing: none` requires `performance: still`, `lip_sync: off`, an empty
  `mouths` map, and `body`/`video`/`cues`/`sync` all `null` — no character
  presence and no retained character asset.
- `performance: animated` requires `body: null`, an empty `mouths` map,
  `cues: null`, `lip_sync` in `off`/`baked`, and a real `video` reference
  (a finished, already-synced muted MP4) — animated performance is driven
  by the supplied video, never a rig or sprite cues authored here.
- `performance: still`/`puppet` requires `video: null` and `lip_sync !=
  baked` (baked sync only applies to a supplied animated video), plus a
  real `body` reference (an approved character image).
- `lip_sync: cues` requires a real `cues` reference, at least two entries in
  `mouths` including a `rest` key, and `sync: null`. Any other `lip_sync`
  value requires an empty `mouths` map and `cues: null`.
- `lip_sync: baked` requires a real `sync` reference (see Sync Receipt
  below); any other value requires `sync: null`.
- Every `mouths` key is a slug identifier (e.g. `rest`, `open`, `wide`); its
  value is a real reference to a mouth PNG. All mouth images across one plan
  must share one aligned canvas size — a differently sized mouth image fails
  `input_check`. A matching canvas size is necessary but not sufficient for
  true alignment: `input_check` only compares dimensions, never mouth
  position within the frame, so it never guarantees the mouth shapes actually
  line up over the character body.
- Every "real reference" field (`body`, `video`, `cues`, `sync`, and every
  `mouths` value) must name a key already present in the plan's `assets` map
  — never a future/unhashed path.

## Audio Contract

`audio` keys are exactly `mode, master, script, receipt, captions, timing`.

- `mode: none` requires all five other audio fields `null`, and requires
  `character.lip_sync: off` — lip sync always needs narration to sync to.
- `mode: speech` or `mode: mix` both require real `master` (finished audio
  master WAV) and `script` (the approved spoken script, `.txt`) references.
- `mode: mix` additionally requires a real `receipt` (finished Audio Mix
  receipt) reference; `captions`/`timing` are optional real references. Any
  other mode requires `receipt`/`captions`/`timing` all `null`. When
  supplying a Mix bundle, read the parent root's shared Mix receiving
  reference before staging it:

  ```text
  skill_view(name="video-creator-pipeline", file_path="references/mix.md")
  ```
- At runtime (`input_check`), the master WAV must be 48 kHz mono/stereo
  PCM16 and its decoded duration must match `duration` within one frame
  (1/30s); the `script` file's normalized (whitespace-collapsed) text must
  equal the concatenation of every unit's `narration`, in order, exactly.

## Units / Copy / Samples Contract

- `units`: `1..24` entries, keys exactly `id, start, end, goal, narration,
  before, change, after`. `id` is a unique slug. `start`/`end` are seconds
  in `0..duration`; units must tile the timeline with no gap or overlap
  (`start` of each equals `end` of the previous, first `start` is `0`, last
  `end` equals `duration`). `goal`/`before`/`change`/`after` are each
  1..2000 characters. `narration` is 1..600 characters, or may be an empty
  string when `audio.mode` is `none` (a silent explainer can never silently
  drop narrated text some other way) OR when `audio.script` is still `null`
  (a genuinely pending, not-yet-supplied script, reported in `pending`) —
  a `pending-inputs` preliminary proposal may leave a unit's `narration`
  empty rather than invent placeholder text before the real script arrives.
   A ready spoken/mixed proposal requires a real `script`
   reference and every unit's `narration` must already be real, nonempty
   spoken text whose concatenation exactly matches that script. Explicitly
   silent proposals require no script or audio and keep every narration empty.
- `copy`: `1..160` on-screen text rows, keys exactly `id, text, start, end`.
  `id` is a unique slug; `text` is 1..2000 characters; `start`/`end` are
  seconds in `0..duration` with `end > start`.
- `samples`: `3..80` ordered, unique `at` times (each `0..duration -
  1/30`) with a short `expect` string (1..2000 chars) each. The first
  sample must be at exactly `0`; the last must be at exactly `duration -
  1/30` (the last representable frame at 30fps). Every unit and every copy
  row needs at least one sample strictly inside its `start..end` interval,
  so every declared beat has actual proof evidence, not just structural
  timing. A `version: 2` (Motion Canvas) plan additionally requires every
  sample's `at` to land exactly on a 30fps frame.

## Mouth Cue JSON (`cues`, only when `lip_sync: cues`)

`propose` compiles an already-supplied, already-reviewed cue file into
`mouth-track.js` in the source's `assets/` directory; it never infers mouth
shapes from text, ASR or raw audio. The cue file's keys are exactly `version, master_sha256, voice,
voice_sha256, offset, events`:

```json
{
  "version": 1,
  "master_sha256": "<sha256 of the plan's audio.master>",
  "voice": "assets/voice-clip.wav",
  "voice_sha256": "<sha256 of that asset>",
  "offset": 0,
  "events": [
    {"start": 0.2, "end": 0.6, "mouth": "open"}
  ]
}
```

The mouth returns to `rest` automatically after the last event's `end`; a
trailing zero-length `{"start": end, "end": end, "mouth": "rest"}` event is
invalid (`end > start` is required) and must never be added.

- `version` must be `1`; `master_sha256` must equal the plan's bound
  `audio.master` hash — cues name a specific frozen master, never a
  different or future one.
- `voice` is a plan asset whose hash matches `voice_sha256`; its decoded WAV
  duration bounds every event's `start`/`end` (both `0..voice duration`,
  `end > start`), and `offset + voice duration` must fit within `duration`
  plus one frame. `voice` must already be a key in the plan's `assets` map
  like every other reference — in simple `audio.mode: speech`, it is the
  same raw speech WAV as `audio.master`; when `audio.mode: mix`, it is the
  distinct, un-mixed dry voice WAV that fed the Mix master, not the mixed
  master itself.
- `events`: `1..4000` entries, keys exactly `start, end, mouth`, ordered and
  non-overlapping (each `start >= previous end`), each `mouth` naming a key
  already in `character.mouths`.
- The generated `mouth-track.js` writes each mouth's opacity once per boundary:
  `1` for the active mouth and `0` for the others. Coincident end/start events
  resolve to the next cue, not an intermediate rest state. This avoids competing
  same-property tweens on reverse seeks. All writes use the scene's own
  `explainer` timeline; `freeze` refuses
  a plan whose `mouth-track.js` bytes (in the source's `assets/` directory)
  differ from what these exact cues would regenerate.

## Sync Receipt JSON (`sync`, only when `lip_sync: baked`)

For `performance: animated` with `lip_sync: baked`, `sync` names a plan
asset whose JSON keys are exactly `master_sha256, video_sha256`, matching
the plan's bound `audio.master` and `character.video` hashes:

```json
{"master_sha256": "<sha256 of audio.master>", "video_sha256": "<sha256 of character.video>"}
```

This binds bytes only. It is not evidence the supplied video's mouth
movement actually matches the narration — that stays an unverified,
externally-produced claim; VideoCreator authors no lip-sync itself for a
baked video.

## Source Contract (HyperFrames, `renderer: hyperframes`)

This section is the HyperFrames HTML/CSS/GSAP source contract only. A
Motion Canvas (`renderer: motion-canvas`, `version: 2`) plan has its own,
unrelated `scene.tsx`/`scene.meta` source contract — see
[motion-canvas](motion-canvas.md).

- One standalone `index.html` with `#root`:
  `data-composition-id="explainer" data-start="0" data-width="<plan
  width>" data-height="<plan height>" data-duration="<duration>"
  data-fps="30"`, matching the approved plan's `aspect`. No template
  wrapper; root background is opaque. Keep every HTML id unique.
- Copy every asset — including the vendored `gsap.min.js`,
  `GSAP-LICENSE.txt`, `gsap-provenance.json` and, when present, the
  generated mouth track — byte-unchanged from the APPROVED proposal's
  already-staged `assets/` directory into the explainer source's `assets/`.
  Never re-copy GSAP from this hands' sibling `../tour/assets/` while
  authoring (or re-authoring, on a resumed proposal) source: `propose` is
  the only step that vendors GSAP from there, and a sibling vendor update
  between `propose` and `freeze` would silently diverge from the hashes
  already frozen in the approved plan, failing `freeze` with "source assets
  differ from approved inputs". Every other asset stays local under
  `assets/`; PNG/JPG/WebP only for images.
- Build synchronously: `const tl = gsap.timeline({paused:true});`, explicit
  time-positioned tweens, then `window.__timelines ||= {};
  window.__timelines["explainer"] = tl;`. When `lip_sync: cues`, the mouth
  track is a plain function DECLARATION with no registry access at load
  time — load it as an external `<script>` in `<head>`, before the inline
  scene `<script>`, and call it exactly once, synchronously, on the same
  `tl`, BEFORE `window.__timelines["explainer"] = tl;` (HyperFrames 0.8.31
  coalesces inline body scripts after external scripts, so an inline
  immediately-invoked version at load time does not see `tl` yet):

  ```html
  <head>
  <script src="assets/mouth-track.js"></script>
  </head>
  <body>
  <script>
  const tl = gsap.timeline({paused: true});
  // ...time-positioned tweens...
  addExplainerMouthTrack(tl);
  window.__timelines = window.__timelines || {};
  window.__timelines["explainer"] = tl;
  </script>
  </body>
  ```

  No autoplay, clocks, timers, randomness, external requests, hover/scroll
  triggers or runtime DOM creation. Prebuild every state; seek it via
  timeline.
- Exactly one element per `copy` row, its `id` matching the row's `id`,
  containing exactly that row's text as rendered plain text (nested
  `<span>`s for staged reveal are fine; the checker only
  whitespace-normalizes them, never rewrites). Every other visible text
  outside `<script>/<style>/<title>` must also live inside a declared copy
  id's element.
  Partial-duration copy uses a `clip` class and exact `data-start` and
  `data-duration` attributes matching the approved hold. Full-duration copy
  may omit both timing attributes. Inspect visibility in actual frames too.
- Character placement: with `framing != none`, an element `id="character-body"`
  — `<video muted ...>` when `performance: animated`
  (`src` = `character.video`), else `<img>` (`src` = `character.body`).
  With `framing: none`, no `character-body` id may exist at all. Only
  `id class src style preload data-start data-duration data-track-index
  data-media-start data-volume muted playsinline` attributes are allowed on
  any `<audio>`/`<video>` element; `data-start` must be `0` and
  `data-duration` must equal the plan `duration`; `data-media-start` must
  be absent or `0` and `data-volume` must be `1` (no retiming/gain).
- Mouth images: with `lip_sync: cues`, one `<img id="character-mouth-<name>">`
   per `mouths` key, `src` = that mouth's asset path, with an
   inline `style` opacity of exactly `1` for the initial mouth and `0` for
   every other mouth. Normally the initial mouth is `rest`; when the first
   cue starts at master time zero (`offset + start == 0`), it is that cue's
   mouth instead. Initial paint and reverse seeks to zero must agree. The
   generated function adds only timeline sets, not off-timeline initializers.
- Audio: with `audio.mode != none`, exactly one `<audio>` element, `src` =
  `audio.master`, unmuted, unity volume, spanning the full duration. With
  `audio.mode: mix`, follow the shared Mix caption/timing binding described
  in the parent root's Mix receiving reference (see the Audio Contract
  section above); `mix_audio.py`'s existing checks are reused unchanged,
  never reimplemented here.

## Freeze / Snapshot / Render

```sh
~/ghq/github.com/NousResearch/hermes-agent/venv/bin/python ${HERMES_SKILL_DIR}/scripts/explainer.py propose \
  --spec <spec>.json --out <deliver>/proposal-v1
# spec.assets maps staged asset names to local files (not yet hashed);
# prints RESULT with status pending-inputs|awaiting-approval and approval_sha256

~/ghq/github.com/NousResearch/hermes-agent/venv/bin/python ${HERMES_SKILL_DIR}/scripts/explainer.py freeze \
  --approved-plan <deliver>/proposal-v1/proposal.md --approval-sha256 <hash> \
  --source <absolute-source-dir> --project <deliver>/explainer-project

~/ghq/github.com/NousResearch/hermes-agent/venv/bin/python ${HERMES_SKILL_DIR}/scripts/explainer.py snapshot \
  --project <deliver>/explainer-project --out <deliver>/explainer-preview
# prints preview_sha256; that folder + hash are what the client approves next

~/ghq/github.com/NousResearch/hermes-agent/venv/bin/python ${HERMES_SKILL_DIR}/scripts/explainer.py render \
  --project <deliver>/explainer-project --approved-preview <deliver>/explainer-preview \
  --approval-sha256 <sha256-of-preview.json> --out <deliver>/explainer-final
```

These same four `propose`/`freeze`/`snapshot`/`render` commands drive a
Motion Canvas (`renderer: motion-canvas`, `version: 2`) plan too, dispatching
internally on `plan.renderer`; only the steps below that mention HyperFrames
by name differ for Motion Canvas, whose own scene-check/render/runtime-
identity behavior is described in [motion-canvas](motion-canvas.md).

- `propose` validates the spec against the schema above, stages the
  vendored GSAP files automatically for a HyperFrames plan (rejecting any
  caller-supplied copy of them; a Motion Canvas plan vendors no GSAP),
  computes every asset's SHA-256, generates `mouth-track.js` under
  `assets/` from approved cues when applicable, and writes `plan.json` + a numbered
  `proposal-vN/proposal.md` embedding the full plan and its SHA-256 —
  `status: pending-inputs` when anything is missing (never a render), or
  `status: awaiting-approval` when the proposal is executable. `can_render`
  mirrors that. This step never authors `index.html`/`scene.tsx` or touches
  HyperFrames/Motion Canvas itself.
- `freeze` requires the exact `proposal.md` bytes (checked against
  `--approval-sha256`) with `Status: awaiting-approval`, re-validates every
  input asset (image bounds, WAV format/duration, character video codec/
  dims, mouth-track bytes, script-vs-narration text match), validates the
  authored `index.html` against the plan (markup structure, copy ledger via
  the ad leaf's reused exact-copy checker, character/mouth/audio placement)
  for a HyperFrames plan, or the frozen `scene.tsx`/`scene.meta` source for
  a Motion Canvas plan, and copies the source into a fresh, exclusive
  `--project` directory, re-verifying the source is byte-identical before
  and after the copy.
- `snapshot` re-validates the frozen project; for HyperFrames it runs
  `hyperframes check` (contrast must be enabled and nonzero) and `snapshot`
  at every sample time, for Motion Canvas it runs the pinned local runtime
  in `snapshot` mode; either way it binds project integrity + frame hashes +
  check hash into `preview.json`, whose own SHA-256 is what the client
  approves.
- `render` requires both `--approved-preview` and its exact
  `--approval-sha256` — no bypass — re-validates every bound frame/check
  hash, re-runs the same engine-specific check/render step as `snapshot`
  (strictly at 30fps), fully decodes the output with `ffmpeg`, checks
  codec/pixel-format/dimensions/duration/fps/audio-presence-vs-plan with
  `ffprobe`, and for any audio track measures true peak with
  `mix_audio.measure_audio` (rejecting silent/unmeasured/clipping output)
  before writing `qa.json` with `semantic_review: pending`,
  `temporal_review: sampled only`, `listening: unverified`, `lip_sync:
  unverified` (unless `lip_sync: off`, which reports `not-requested`), and
   `media_generation: 0`. It also records the selected `renderer` and the actual
   `contrast` audit object. Motion Canvas reports contrast as disabled with a
   manual-review reason; the final QA text preserves that visual-review gap.

All outputs must be fresh directories, never nested inside source/project/
preview. Paths are absolute, physical and symlink-free.

## Compatibility

This leaf is standalone: composition id `explainer`, not `tour` or `ad`. It
reuses only `tour.py`'s/`authored.py`'s low-level file, hash, image and
HyperFrames-CLI primitives and the `ad` leaf's exact-copy checker through
explicit path imports — never their scaffold/freeze/render dispatch, and
never edits any of those files.

## Runtime Identity

The preview records the resolved HyperFrames executable and its version for
a HyperFrames plan; a Motion Canvas plan instead records its own pinned
runtime/Node/browser identity, per [motion-canvas](motion-canvas.md).
Render rejects a different executable/version: make a new preview and get
approval, never upgrade frozen input or approve a newly computed hash
yourself. This guards reported CLI drift, not all browser/OS/font
differences. Supplied WOFF2 fonts, if used, are hash-bound assets;
installed system fonts remain an explicitly disclosed environment
dependency.
