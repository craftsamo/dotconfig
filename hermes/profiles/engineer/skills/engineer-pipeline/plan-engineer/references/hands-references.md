# Hands option-backed references

Read when the agreed outcome touches an image-creator/video-creator/
audio-creator hands leaf's option-backed reference catalog: adding a style,
theme, destination, pack or content option, or improving one from supplied
evidence. Never Writer's language references, Creator's broker guidance, a
new media family/leaf, or option retirement; route those to their own workflow.
OpenCode owns the maintenance procedure through the candidate checkout's
`opencode/skills/hermes/hands-references/SKILL.md` (hermes-hands-references).
Engineer owns the Client agreement, not a duplicate authoring procedure.

1. Infer the target leaf/field from the desired outcome and current sources.
   If unresolved, ask what capability should improve or offer a bounded
   [Assess](../../assess-engineer/references/hands-references.md) inventory. Do not ask the Client to
   design a file tree or authorize a speculative rewrite of every profile.
2. Use opencode_call with agent="plan" under the common transport contract.
   Include the candidate Skill path to read and the actual request/evidence;
   do not paste its body or rely on a new tool parameter or global install.
   Ask for affected consumers and acceptance checks, not edits. Unsupported
   renderer behavior is a capability change needing explicit scope, not prose.
3. Agree addition versus improvement, intended quality change, evidence/source,
   affected consumers and checks. A status upgrade needs evidence with its
   limits retained; no research result implicitly authorizes paid calls,
   uploads, authenticated inspection or test posts.
4. Under the normal [Plan](../SKILL.md) contract, one explicit implementation
   approval releases only that scope to [Build](../../build-engineer/references/hands-references.md).
   Decide required structural checks, instruction-following tests and any real
   render proof separately. No automatic Issue, merge or live-cutover grant.
