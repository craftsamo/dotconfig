# Web UI direction

Read the [design catalog](../shared/design-catalog.md) as optional design
knowledge, not a compulsory style menu. Engineer owns the consultation with the
Client; OpenCode implements the chosen result. Existing design systems and an
explicit Client brief outrank defaults. A small adjustment preserves the current
direction without a new design ceremony.

1. Identify intended users, important flows, target devices and the existing
   look. Preserve supplied copy, brand decisions, assets and constraints.
2. Existing design system: extend it. Client-named mood: propose a concrete
   interpretation with type, palette, density, shape and hierarchy. Reference
   site: Engineer opens the permitted reference in its own isolated browser,
   inspects screenshots and extracts choices. Reference access is not permission
   to copy/upload private assets or use the owner's login.
3. If direction remains genuinely unresolved, propose 2-3 alternatives. When
   visual comparison would help, ask permission for a bounded disposable style-
   tile implementation through OpenCode's build agent, in a separate fixture
   worktree. This is a prototype-only release, not approval to implement the
   product. The plan agent does not write HTML or produce imaginary screenshots.
4. Agree the direction, relevant tokens, layout priorities and states with the
   Client. Suggestions remain proposals until decided; do not choose taste
   silently. Pass the accepted choices to [Build](../build/web-ui.md) and
   [visual QA](../quality-assurance/web-ui.md).

Substantial prose/media stays with its producer or the supplied inputs. UI design
consultation does not authorize new claims, image generation, paid assets or
production access. A pending asset remains pending in the plan, not a fabricated
path. Record direction changes explicitly so old screenshots/approvals are not
used as evidence for a newly designed state.
